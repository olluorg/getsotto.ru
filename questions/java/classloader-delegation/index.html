Что такое class loader и как работает делегирование загрузки классов?

MiddleJVM и сборка мусора
Ещё спрашивают так:
  • Зачем загрузчики классов сначала делегируют загрузку родителю?
  • Зачем загрузчики классов сначала делегируют загрузку родителю (parent-first)?
Коротко

ClassLoader находит байт-код и превращает его в класс. Иерархия: Bootstrap (ядро JDK) → Platform (модули платформы) → Application (classpath). Модель parent-first: запрос сначала идёт к родителю, и только если тот не нашёл — загрузчик ищет сам.

  • Защита: свой java.lang.String в classpath не подменит системный
  • Класс в JVM определяется парой «полное имя + загрузчик»
  • Исключения: сервлет-контейнеры грузят классы приложения первыми (child-first)

Подробно

Иерархия загрузчиков (Java 9+):

  • Bootstrap — встроенный в JVM, грузит java.base и ядро;
  • Platform — остальные модули Java SE и JDK;
  • Application (System) — классы из classpath и module path приложения.

Делегирование. loadClass сначала проверяет, не загружен ли класс, затем просит родителя, и только при неудаче вызывает свой findClass. Зачем:

  • безопасность — классы платформы всегда приходят от доверенного загрузчика, подменить java.lang.String нельзя;
  • единственность — базовый класс загружается один раз, а не каждым загрузчиком отдельно.

Идентичность класса. Один и тот же байт-код, загруженный двумя загрузчиками, — два разных класса. Отсюда «ClassCastException: Foo cannot be cast to Foo». На этом же построена изоляция: плагины и веб-приложения используют разные версии одной библиотеки.

Отступления от parent-first: сервлет-контейнеры (Tomcat) сначала ищут в WEB-INF приложения, чтобы его библиотеки не перекрывались серверными; OSGi и системы плагинов строят граф загрузчиков. Для SPI используют контекстный загрузчик потока (Thread.getContextClassLoader).

Загрузка ленивая: класс загружается и инициализируется при первом активном использовании.
