Что такое Liskov Substitution Principle и что обязан соблюдать подтип?

MiddleПринципы проектирования

  • Объясните Liskov Substitution Principle и приведите пример нарушения — желательно из стандартной библиотеки Java.
Коротко

Подтип должен быть подставим вместо базового типа без сюрпризов для вызывающего: не усиливать предусловия, не ослаблять постусловия, сохранять инварианты, не бросать новых исключений, которых клиент не ждёт. Это про поведение, а не про компиляцию.

  • Классика: Square extends Rectangle — setWidth меняет и высоту
  • В JDK: Arrays.asList и List.of бросают UnsupportedOperationException на add
  • Stack extends Vector открывает доступ по индексу

Подробно

Формулировка: если S — подтип T, то объекты T в программе можно заменить объектами S, и корректность не пострадает.

Правила контракта:

  • предусловия нельзя усиливать — подтип не может требовать от вызывающего больше (принимать только положительные числа, когда базовый принимал любые);
  • постусловия нельзя ослаблять — подтип не может гарантировать меньше;
  • инварианты базового типа сохраняются;
  • правило истории — подтип не меняет состояние способами, невозможными для базового (изменяемый подкласс неизменяемого типа).

Пример:

void resize(Rectangle r) {
    r.setWidth(5); r.setHeight(4);
    assert r.area() == 20;   // для Square — 16
}

Квадрат математически — прямоугольник, но изменяемый квадрат не ведёт себя как изменяемый прямоугольник.

В JDK: List.add у Arrays.asList и List.of бросает UnsupportedOperationException — формально документировано как «необязательная операция», но клиент, получивший List, не может на add положиться.

Как избежать: наследовать только при настоящем «является» по поведению; предпочитать композицию; делать иерархии неизменяемыми.

Частые ошибки

  • «Подтип должен переопределять все методы» — не относится к LSP.
