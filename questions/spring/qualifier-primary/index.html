Как разрешить неоднозначность, когда для внедрения подходят несколько бинов одного типа?

MiddleIoC и внедрение зависимостейSpring
Ещё спрашивают так:
  • Что делать, если найдено несколько бинов одного типа?
Коротко

При нескольких кандидатах — NoUniqueBeanDefinitionException. Решения: @Primary — бин по умолчанию; @Qualifier("имя") — выбрать конкретный в точке внедрения (он сильнее @Primary).

  • Совпадение имени параметра с именем бина тоже работает как квалификатор
  • Свои аннотации-квалификаторы (@Fast, @Reliable) — типобезопаснее строк
  • Внедрить все: List<PaymentGateway> или Map<String, PaymentGateway>

А ещё Много неоднозначностей — повод для стратегии с выбором в рантайме

Так подсказку видит пользователь sotto на живом собеседовании — за пару секунд, пока вы думаете вслух.

Подробно

Проблема: интерфейс PaymentGateway реализуют CardGateway и SbpGateway. Внедрение PaymentGateway gateway неоднозначно — контекст не стартует.

@Primary на одной реализации делает её выбором по умолчанию для всех точек внедрения без уточнения.

@Qualifier в точке внедрения выбирает бин по имени (или по значению квалификатора): @Qualifier("sbpGateway") PaymentGateway gateway. Квалификатор приоритетнее @Primary.

По имени параметра: если имя параметра совпадает с именем бина (PaymentGateway sbpGateway), Spring выберет его — но это хрупко при переименовании.

Свои квалификаторы — аннотация, помеченная @Qualifier: @Sbp PaymentGateway gateway. Ошибки ловятся компилятором.

Все реализации сразу: List<PaymentGateway> (в порядке @Order) или Map<String, PaymentGateway> (ключ — имя бина) — для стратегии, где выбор делается в рантайме по типу платежа.

  • Внедрение всех реализаций.

Частые ошибки

  • Полагаться на имя параметра как на квалификатор.
